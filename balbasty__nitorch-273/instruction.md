# Issue

**Title:** FEAT(register): @nonlin shoot --exact for exact geodesic shooting

## Description

Part of #171. `spatial.shoot(fast=True)`, the default used by registration, does not converge to the geodesic as `--steps` grows. This PR measures the problem and adds an opt-in exact scheme. **The default stays fast, unchanged bit for bit** (owner decision).

## Why fast doesn't converge
- **Exact** (`fast=False`): at each step the initial momentum is transported along the integrated warp, m_t = push_{Φ_t}[(DΦ_t)^-T m_0]. m_0 is splatted fresh each step.
- **Fast**: chains one-step transports, m_t = push_{id+dt·v}[(I − dt·Dv)^T m_{t−dt}].
  - Each linear splat re-blurs the *current* momentum, so the smoothing compounds.
  - The total blur is about |v| voxels², whatever the number of steps.
  - Measured: moving noise by a fixed shift of 10 voxels with N linear splats gives an effective variance of 1.0 / 3.8 / 7.0 / 9.0 at N = 4 / 16 / 32 / 128, against 1.0 / 3.75 / 6.9 / 9.2 predicted.
- The first-order step factor (I − dt·Dv)^T is not the cause. Replacing it with the exact (I + dt·Dv)^-T gives the same results as fast for N ≥ 16.

## Measurements (CPU, float32; reference = exact with 256 steps)
Error on the inverse warp φ, mean / max in voxels, 3D 48³, |v|max = 10:

| steps | fast | exact |
|---|---|---|
| 8 | .056 / .19 | .034 / .10 |
| 32 | .090 / .32 | .0077 / .023 |
| 128 | .100 / .36 | .0011 / .0033 |

- **Other cases:** |v| = 5 or 20, a sharper field, and 2D all behave the same way. The exact scheme converges at about 1/steps; fast levels off or gets worse.
- **Energy kept along the path, ⟨m_T, v_T⟩ / ⟨m_0, v_0⟩ (3D):** exact keeps about 0.80, the same as the reference, whatever the number of steps. Fast keeps 0.53–0.57 at 8 steps, falling to 0.34–0.52 at 128.
- **Cost at 64³:** exact takes 1.4–1.7× as long per shooting call, or 1.3–1.4× when the inverse is also computed.
- **Short symmetric registration** (64³ pair, 10 GN iterations):

  | | fast | exact |
  |---|---|---|
  | wall time | 58 s | 66 s (+14%) |
  | \|ψ∘φ − id\|, mean / max | .083 / .79 | .046 / .42 |
  | recovered warp, mean error | about 1.0 vox | about 1.1 vox |

  A velocity fitted with one scheme must be re-shot with the same scheme: re-shooting a fast-fitted velocity with the exact scheme moved the warp by about 3 voxels.

## Changes
- **`register` parser:** `@nonlin shoot --exact [BOOL]`, long option only, default `false`. `svf` and `smalldef` reject it. `--exact false` is the explicit default; there is no separate `--fast`.
- **`register` CLI:** passes `fast = not exact` to the model.
- **`objects.py`:**
  - `ShootModel(fast=True)` passes `fast` to every `spatial.shoot` call (`exp`, `iexp`, `exp2`).
  - New `NonLinModel._init_options()`, so pyramid copies keep both `inversion` and `fast`.
  - `repr` shows `fast=False`.
- **Sidecar:** `register` already wrote `"fast"` to `{name}.json`, and `reslice`/`compose` already passed it to `shoot`, so no change was needed. The value now reflects the actual choice. JSONs without the key use fast.
- **`vexp`:** unchanged. It exponentiates stationary velocities only and never shoots.
- **Docs (`register.md`, `reslice.md`, `compose.md`, `vexp.md`):**
  - an `--exact` option row;
  - a section "Fast or exact shooting with `--exact`" with the figures above and when to use it;
  - the `fast` key in the `{name}.json` description;
  - the scheme follows the JSON in reslice/compose;
  - vexp doesn't shoot.
