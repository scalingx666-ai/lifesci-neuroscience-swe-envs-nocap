# Issue

**Title:** FIX(register): mutual information gradients, geometric norm, slicewise

## Description

Part of the fixes from the `nitorch register` audit (group B: mutual information, `losses/mi.py`).

## Summary
- **`--norm arithmetic`: wrong gradient.** The `(1+log pxy)` term had the wrong sign. The loss is `hxy/(hx+hy)`, whose gradient is `[-(1+log pxy) - nmi·((1+log px)+(1+log py))]/(hx+hy)`. Finite-difference (FD) cosine goes from −0.748 to +1.0000.
- **`norm=None` (Python API default of `make_loss('mi')`): value/gradient mismatch.** The value was divided by H(fixed) but the gradient and Hessian were not (ratio 2.06 = H(fixed)). The value is now `−MI`, as documented in `mi()` and `make_loss`, so `None` matches `norm='no'`. Gradient and Hessian, and therefore Gauss-Newton steps, are unchanged. The CLI never used `None` (its default is `studholme`).
- **`--norm geometric` silently ran plain MI.** It is now implemented: loss `1 − MI/√(Hx·Hy)`, with an FD-verified gradient and a Hessian approximation following the same pattern as the other norms. Unknown norms now raise instead of falling back to plain MI.
- **`@loss mi -z` (slicewise) crashed**, with and without a mask:
  - With a mask, the masked voxel count had the wrong shape. Slices with an empty mask now give zeros instead of NaNs.
  - Without a mask, the TorchScript `grid_count` failed on batched grids (`_C/_ts/pushpull.py`: its input of ones had batch size 1). Batch-1 output is unchanged.

**Studholme NMI (the default, used by `affreg`) is unchanged:** value, gradient and Hessian are bitwise identical to master, in float32 and float64, with and without a mask.

## Tests
New `nitorch/tests/test_register_mi.py` (22 tests):
- FD gradient checks for all five norms;
- value checks against an independent entropy computation;
- an unknown-norm error;
- slicewise FD checks for four norms, with and without a mask;
- an empty-slice mask;
- a batched `grid_count`.

On master, 16 of the 22 fail. All pass here. `nitorch/tests` (non-gradcheck) passes, and so do the 336 `test_gradcheck_spatial.py -k count` tests on the TS backend.

End to end, the recovered translations (true value (4, −2, 6) mm) are:
- `@loss mi -m geometric`: (3.99, −1.99, 5.99);
- `@loss mi -m arithmetic`: (3.99, −2.02, 5.96).

## Found, not fixed here
- Slicewise MI with GN converges very slowly. The gradient is FD-correct, so the Hessian approximation on sparse per-slice histograms is probably very conservative.
- `@loss mi --order` is ignored. This is fixed in the "ignored options" PR, which also sets its default to 1 because the joint-histogram Hessian only supports order ≤ 1.
- The TorchScript `nd.push` (spline order ≥ 2) also fails on batched grids, so slicewise MI with `spline ≥ 2` still fails.
