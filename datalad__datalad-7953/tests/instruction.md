# Issue

**Title:** BF: tab (and unicode again) in OBSCURE_FILENAME, and fix what they expose

## Description

### Overview

While auditing how  hands DANDI asset paths to git/git-annex, I based its tests on `OBSCURE_FILENAME` and found it less obscure than intended:

1. **Regression since 1.3.2**: d845b0319 (#7814) turned `if <fs encoding is utf-8>:` into `if not (FILESYSTEM_SUPPORTS_UTF8 := ...):`, so `UNICODE_FILENAME` is only tried where the encoding is *not* UTF-8, where the filesystem probe then rejects it. On Linux/macOS, `OBSCURE_FILENAME` has been `' |;&%b5{}\'"<> .datc '`, with no unicode.
2. **No control character.** Git and git-annex C-quote such paths in line-based output even with `core.quotepath=false`, and a tab is the path separator in `ls-files --stage`/`ls-tree`. This PR adds `'\t'` to `OBSCURE_FILENAME_PARTS`; filesystems that reject it (Windows) skip it like other parts. The name is now `' |;&%b5{}\'"<>\tΔЙקم๗あ .datc '`.

Restoring unicode alone causes no new failures. Adding the tab made 18 tests fail and exposed two bugs, both fixed here:

- `GitRepo.get_content_info()`: the greedy `(?P<sha>.*) (.*)\t` regex ran up to the *last* tab. A clean dataset's `status` therefore reported a file with a tab in its name as `deleted`, plus its post-tab remainder as `added`, which in turn broke `save` and `run` on such files. `get_submodules_()`'s `split('\t')` raised `ValueError` on such a submodule path.
- `AnnexRepo.unannex()` parsed human-readable output, and `_unquote_annex_path()` only undoes `\"`, so paths with a tab or backslash came back mangled. It now uses `--json` (`call_annex_records`), as that helper's docstring recommends. `_unquote_annex_path()` is now unused; I left it in place in case extensions call it.

`test_AnnexRepo_always_commit` mimics git-annex's quoting in `git annex log` output and now escapes `\` and tab as well.

### Not included, possible follow-ups

Other characters I considered for `OBSCURE_FILENAME_PARTS`:

- `[1]`, `*`, `?`: Git pathspecs and fnmatch globs. They would change the semantics `GlobbedPaths`/`run --input` are documented to have, so tests there would need rethinking.
- A leading `-` or `:` (option and pathspec-magic injection): incompatible with the leading space.
- `\n`: breaks every line-based protocol; `get_content_info()`'s regex also lacks `re.DOTALL` for it.

In backups2datalad, the `[1]` glob case caught a real data-loss bug (`git rm -- 'foo[1].txt'` also removes `foo1.txt`).
