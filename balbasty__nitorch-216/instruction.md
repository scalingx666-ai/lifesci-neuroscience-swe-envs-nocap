# Issue

**Title:** PERF(spatial): pool and conv use the native path for every zero-padding alias

## Description

Part of #171. This is a , for an issue found while working on that PR.

`spatial.pool` and `spatial.conv` took torch's fast native-padding path only when `bound == 'zero'`. The equivalent spellings `'zeros'` and `'constant'`, in any capitalisation, went through a slower explicit `utils.pad` and gave identical results. `pool` defaults to `'constant'`, so a call with the default bound never got the fast path. `smooth` calls `conv`, so it benefits from this fix as well.

**Change:** a new helper, `_is_zero_bound(bound)`, normalises the name with `core.bounds.to_nitorch`. It also accepts a list of bounds, in which case every entry must be zero, and returns False for anything it cannot parse. `pool` and `conv` now use it. For other bounds, the original `bound` value is still passed to the explicit-pad path unchanged.

**Tests:** the new `nitorch/tests/test_pool_bounds.py` has 15 tests.
- A call counter on `utils.pad` checks that each alias skips the explicit pad.
- For mean and max pooling, the results match `bound='zero'`, and they match manual padding (with a −inf fill for max).
- `dct2` still pads explicitly.
- `conv` gets the same alias check.
- Before the fix 9 tests fail; after it all 15 pass. `pytest -k "pool or conv"` gives 71 passed and 4 skipped.

**Behaviour:** results are unchanged; only the speed changes.
