# Issue

**Title:** FIX(resize): -g grid mode, -v with -f

## Description

Part of #171.

1. **`-g`** crashed. With `affine=`, `spatial.resize_grid` returns `(grid, affine)`, both with a batch dimension. The CLI took `[0]` of that pair and then unpacked the grid tensor into two names. It now unpacks the pair and drops the batch dimension from both.
   - **Also fixed:** `-g t` was treated like `-g d`, which the docs listed as a caveat. `resize_grid` only treats a type starting with `g` as a transformation, so the CLI now passes `'grid'` for `t` and `'displacement'` for `d`.
2. **`-v` with `-f`** raised an uncaught `ValueError`. The docs say the two cannot be combined, so the parser now checks this right after parsing and raises a `ParseError`: it prints the help and an `[ERROR]` line, with no traceback.

**Docs (`resize.md`)**
- The "-g is not working" warning is replaced by a short section on how `d` and `t` fields are rescaled.
- The `-v` description now says that combining it with `-f` is an error.

**Tests:** the new `nitorch/tests/test_cli_resize.py` has 4 tests.
- A displacement field with `-g d -f 2`, with anchors `centers` and `first`. Each run checks the shape, the voxel size and the origin, and that the values are multiplied by the ratio of input to output voxel size.
- An identity transformation field with `-g t` stays the identity on the output grid.
- `-f` with `-v` gives an `[ERROR]` with no traceback and no output file.
- All 4 fail before the fix and pass after it.

**Behaviour change:** `-g t` now rescales the field as absolute coordinates, not as displacements.

**New issues noticed, not fixed here** (added to #171):
- With `-g` and the anchors `first`/`last`/`edges`, output voxels outside the input field of view become 0. That follows the documented rule, but for a displacement field it gives a zero border.
- Giving none of `-f`/`-v`/`-s` still raises an uncaught `ValueError`.
- The `except Exception` handler in `resize()` is commented out.
