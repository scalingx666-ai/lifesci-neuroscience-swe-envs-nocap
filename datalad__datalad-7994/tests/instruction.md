# Issue

**Title:** BF: extract a tarball's links as copies where 7z cannot create links

## Description

On a filesystem without links, such as VFAT, the `datalad-archives` special remote cannot retrieve *any* file from a tarball that contains a symlink or a hard link:

```
Failed to fetch any archive containing ...
```

Seen as datalad-next's `test_replace_add_archive_content` failing in its `test-linux-crippled` job (TMPDIR on VFAT) on Ubuntu 26.04 runners.

### Cause

- 7-Zip for Linux (21.x and later, which replaced p7zip 16.02 in distributions) recreates a tarball's symlinks and hard links with `symlink()`/`link()`.
  - No switch avoids that: `-snh-` does not affect tar hard links, and `-snl-` drops symlinks instead of copying them.
- On VFAT both calls fail with EPERM:
  - 7z reports `ERROR: Cannot create symbolic link` / `ERROR: Cannot create hard link`, leaves nothing in their place, and exits with 2.
  - 7-Zip 21–24 also report `ERROR: Cannot set file attribute : errno=2 ...` for each hard link they did not create.
- `decompress_file()` raises `CommandError`, so the extraction cache is never stamped, and even the regular files 7z did extract cannot be retrieved.
- p7zip 16.02 wrote a symlink as a text file and a hard link as an empty file, and exited 0.

### Fix

In `datalad/support/archive_utils_7z.py`, when 7z fails, extract the tarball again with `tarfile`, which extracts a copy of the link target when it cannot create a link. The fallback is narrow:

- **stderr:** every non-empty line 7z wrote to it must be one of the errors above, and at least one must be a failure to create a link.
  - Any other error (e.g. `ERRORS: Unexpected end of archive` for a truncated archive, `Cannot open output file`) raises the `CommandError` as before.
  - So does a link pointing outside the archive.
  - Without `-so` or a terminal, 7z writes only errors and warnings to stderr.
- **tarfile:** the fallback runs only where `tarfile` has its `data` extraction filter (Python >= 3.10.12, 3.11.4), which keeps the extraction inside the target directory, and only for a tarball.
- **If `tarfile` fails as well:** the original `CommandError` is raised, chained.

On filesystems that support links, 7z succeeds and nothing changes. No new test: CI has no VFAT job in core, and the behaviour is covered by datalad-next's crippled-filesystem job.

### Testing

`decompress_file()` was run directly, with `link()`/`symlink()` failing with EPERM (strace fault injection) to simulate VFAT. This sandbox's kernel has no vfat driver.

| 7-Zip | sample `.tar.xz` / `.tar` with a symlink and a hard link | symlink-only tar | truncated tars with links | tar with a link escaping the target |
|---|---|---|---|---|
| 21.07, 23.01, 24.09, 25.01, 26.00 | extracted, links as copies | extracted | `CommandError` | `CommandError`, nothing written outside |

- **datalad-next `test_replace_add_archive_content`**, with the special remote run under the same injection: passes with 7-Zip 23.01 and 26.00. Without the fix it fails.
- **`datalad.tests.test_archives`, `datalad.customremotes.tests.test_archives`, `datalad.local.tests.test_add_archive_content`:** 52 passed, in a venv without datalad-next.

Three independent AI reviewers approved this change after three rounds. Their round-2 findings (7-Zip 21–24, truncated archives) are addressed here.
