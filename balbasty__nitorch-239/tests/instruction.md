# Issue

**Title:** FIX(autoreg, orient): write world-to-world LTAs as RAS-to-RAS, not physical

## Description

Part of #171. This follows your decision on the item raised in #207.

**Bug:** `autoreg` (`write_transforms`) and `orient` compute world-to-world affines but wrote them as LTA `type=2` (physical-to-physical).
- **orient:** the transform is `spatial.affine_rmdiv(affine, aff0)`, the new vox2ras times the inverse of the old one, which maps RAS to RAS.
- **autoreg:** `lin` is composed directly with vox2ras matrices (`affine_matmul(lin, moving_affine)` and similar), so it acts in world space.

**Fix:** both call sites now use `io.transforms.save(..., type='ras')`. The matrix is written unchanged, so `fdata()` and `data()` return the same matrix, and only the header type changes, from 2 to 1. A search of `nitorch/cli` and `nitorch/tools` for `type=2`, `LINEAR_PHYSVOX` and `'physical'` finds no other caller.

**Behaviour change:**
- **nitorch readers** (`reslice`, `autoreg -init`, …): unchanged. They read these files through `fdata()`, which already returned the raw matrix, because no volume info was written.
- **External tools that read the header type, such as FreeSurfer:** they now interpret the matrix correctly, as RAS-to-RAS.

**Docs:** a writer subagent added a sentence saying the `.lta` output is a world-to-world (RAS-to-RAS) affine readable by FreeSurfer, in:
- `orient.md`;
- `autoreg.md` (Outputs);
- the registration tutorial's outputs table.

**Tests:**
- `test_autoreg_lta_is_ras_to_ras` captures the matrix during a run.
- `test_orient_transform_is_ras_to_ras` compares against `affine_rmdiv(new, old)`, and also checks that this matrix is not the identity.

Both tests check that `type()` is `('ras','ras')` and that `fdata()` and `data()` equal the computed matrix. Before the fix they fail with `('physical','physical') != ('ras','ras')`. `pytest -k "autoreg or orient or reslice or lta or savef"` gives 170 passed and 9 skipped.
