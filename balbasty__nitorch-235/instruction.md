# Issue

**Title:** FIX(epic): clear errors for too few echoes and -r count; Hessian used uninitialised memory without reverse echoes

## Description

Part of #171. This is a , for issues found while working on it.

1. **Too few echoes for reverse-echo synthesis (reproduced).**
   - **Bug:** two 3D inputs crashed in `synthesize_neg` with `IndexError: index -2 is out of bounds`, and three echoes crashed in `synthesize_pos`. Synthesis needs at least 2 echoes of each polarity, so 4 echoes in total.
   - **`-e` does not help:** synthesis always extrapolates the first and last reversed echoes from two neighbours. `-e/--extrapolate` only decides whether those echoes are used in the fit, so an error suggesting `-e`, or an automatic fallback to it, would be wrong.
   - **CLI fix:** when synthesis would run (no `-r`, no `-x`) and there are fewer than 4 echoes, the command stops before any heavy work with a `ParseError`: `Reverse-echo synthesis needs at least 2 echoes per polarity (4 echoes in total); got N. Use -x/--no-synth, give acquired reversed echoes with -r, or give more echoes.`
   - **Decision:** this is an error rather than a silent switch to `-x`. The docs already state the minimum, and switching would change the algorithm without the user asking.
   - **Tools fix:** a new `check_synth()` makes `epic()` raise a `ValueError` before the `--slicewise` split, so the error does not come from a pool worker. `run_epic()` runs the same check, and `synthesize_neg`/`synthesize_pos` now raise a `ValueError` instead of an `IndexError`.
2. **Uninitialised Hessian without reverse echoes.** In `run_epic_noreverse`, the Hessian for a voxel-shift map was built from `one = torch.empty_like(voxshift)`, which is uninitialised memory. Results with `-x` and a field map therefore depended on whatever was left in memory.
   - It is now `torch.ones_like`, as in `run_epic`.
   - `h = torch.empty_like(echoes)` and `fwd_fit = torch.empty_like(fit)` are fully overwritten afterwards, so they are fine.
3. **`-r` count.** A reversed-echo count that differed from the forward-echo count failed later with a shape error.
   - The CLI now raises `Expected as many reversed echoes (-r) as forward echoes (N); got M.`
   - `epic()` now raises a `ValueError` on a shape mismatch.
4. **`map_files`:** a duplicate `files.dim == 5` term is removed. There is no behaviour change.

**Checked, not changed:** `-r` files are correctly left out of the output count in `check_outputs`. The fit starts from `(echoes + reverse_echoes) / 2` and returns only the forward echoes. A new test checks this.

**Docs:** a writer subagent updated `docs/cli/reference/qmri/epic.md`:
- the description, the `ECHOES` argument, and the `-r` and `-e` rows now give the minimum of 2 echoes per polarity, with `-x` or `-r` as the alternatives;
- they say that `-e` does not lower the minimum;
- they give the `-r` count rule and its error;
- they say that only forward echoes count towards `-o`.

**Tests** (`nitorch/tests/test_cli_epic.py`):
- **Too few echoes:** the CLI rejects `[1,1]`, `[1,1]` with `-e`, and `[3]`, and accepts `[1,1]` with `-x`, `[1,1]` with `-r`, and `[2,2]`; it also checks the error message. At the tools level, 1–3 echoes raise a `ValueError`, with and without `--slicewise`, and so do the single-echo `synthesize_*` calls.
- **Hessian:** `test_noreverse_hessian_is_initialised` replaces `torch.empty_like` with versions filled with NaN, 1e6 and −3, and checks that the output is finite and the same in all three cases.
- **`-r` count:** mismatches are rejected at the CLI and tools levels, and the fit has the shape of the forward echoes.
- **`map_files`:** output shapes.

The test helpers `_run_main`/`_run_outputs` now pass `-x`, because they used 1–3 echoes with default synthesis.

12 new tests fail on master's code. After the fix, `-k epic` gives 51 passed, and the CLI test files give 603 passed and 5 skipped.

**Behaviour changes**
