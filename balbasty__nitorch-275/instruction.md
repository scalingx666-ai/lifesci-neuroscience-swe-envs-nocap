# Issue

**Title:** C backend: fix all test failures (out-of-bounds Hessian reads, batch strides, dtype/shape, RLS fallbacks)

## Description

## Summary
With the compiled backend (`NI_COMPILED_BACKEND=C`), the suite on master had **56 failures**: the 32 found earlier, plus 24 in the newer `test_shoot_autograd.py`. CI only runs the TorchScript backend, so none of them showed up. With this PR, the suite passes on both backends.

Root causes, from most to least serious:

1. **Out-of-bounds reads in the field relax (C++).**
   - `NI_DISPATCH_HESSIAN_TYPE1` (`impl/hessian.h`) is the Hessian dispatch for 2-channel fields. It had no case for a diagonal Hessian (CC == C == 2), which fell through to the ESTATICS layout. That layout reads 2C−1 = 3 values from a 2-channel Hessian.
   - Valgrind reports invalid reads just past the Hessian buffer.
   - Effect: field relax and FMG diverged or returned NaN, with results that varied between processes. This hit every 2-channel field solved with a diagonal Hessian.
2. **Wrong batch stride in the grid regulariser (C++).** `impl/regulariser_grid_common.cpp` computed the Hessian pointer as `hes_ptr + … + n*inp_sN`, i.e. with the input's batch stride. The grid Hessian has D(D+1)/2 channels and the input has D, so their batch strides differ. Batch items after the first therefore read the wrong Hessian. The grid FMG with CG then returned NaN for them, which broke `grid_inv` and the shoot inversion for batched inputs. All 4 occurrences are fixed. A scan of every kernel for pointers offset with another tensor's strides found no other case.
3. **Missing `else` (C++).** In `prepare_tensors` of relax, precond, precond_grid and regulariser, the line after `if (dim == 1)` was `if (dim == 2)`. 1D tensors therefore fell through to the 3D `expand`.
4. **Mixed dtypes (Python, `spatial/_grid.py`).** The compiled kernels require the grid and the image to have the same dtype. The TorchScript ones accept a float32 image with a float64 grid, which is how `register` writes its outputs. With the C backend, the grid is now cast to the image's dtype, which is also the output dtype of the TorchScript kernels.
5. **Low-rank grids (Python, `spatial/_grid.py`).** A grid with fewer output spatial dimensions than components is now left-padded with singletons. The TorchScript kernels already do this implicitly, so TorchScript behaviour is unchanged.
6. **Unsupported penalties (Python, `spatial/_solvers.py` and `_regularisers.py`).** The compiled solvers implement neither per-penalty weight maps (`dict`) nor weighted bending or linear-elastic energies, and used to raise. A new `_c_supports(...)` check sends those cases to the TorchScript solvers instead.
7. **float32 rounding of the linear-elastic penalties (Python, TorchScript side).** `make_vector(lame, 2)` builds a float32 tensor, so the TorchScript regulariser and solver used, for example, 0.05·(1 + 1.5e-8). The C kernels keep the penalties in double, and the two backends now agree to 2e-16.
   - `test_shoot_autograd` compares the autograd path with the no-grad path bitwise. With the C backend these use different kernels (the compiled regulariser has no autograd), so on C the test now allows rounding differences: rtol 1e-10, with 1.8e-12 measured. With TorchScript it stays bitwise.

## Side observations (not changed here)
- The C and TorchScript FMG differ slightly. After the same number of cycles, the C solution is a little less converged: a relative residual of 2.5e-2 vs 1.5e-2 with bending on a 2D grid. Both are valid, but the implementations differ.
- The field bending regulariser of the two backends differs at the borders with `dct2`: a norm of 11.79 vs 11.27 on a 6×5 field. The grid bending regulariser agrees. I didn't investigate which one is right.
- CI does not build or test the compiled backend. A CPU job building it would have caught all of the above.
