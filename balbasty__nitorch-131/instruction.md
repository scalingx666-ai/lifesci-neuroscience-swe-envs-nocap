**Title:** Fix StepSizeLineSearch evaluation point and store_value; drop line-search prints

## Description

Part of #114. , which was merged before these changes were added.

## Summary
- **`StepSizeLineSearch.step`** (`optim/linesearch.py`):
  - It built `param = param0 + lr·delta`, but evaluated the loss at `param.add(delta, alpha=lr)`, i.e. `param0 + 2·lr·delta`, and then accepted `param0 + lr·delta`. It now evaluates the loss at `param`.
  - `store_value` had no effect: it wrote `self.lr` on the wrapper, and `lr` is not a property forwarded to the optimiser. It now matches `BacktrackingLineSearch`: on success, the step size × `store_value` is stored on the optimiser (`setattr(optim, self.key, ...)`), and the optimiser is left unchanged otherwise. The initial step is read through `self.key` as well.
- **`BacktrackingLineSearch.step`**: removed the bare `print('success')` / `print('failure')` added in f264247.
  - The registration progress printer (`pairwise_impl.py`) already reports line-search activity in its own format:
    - at `-v 2`, line-search evaluations are shown as `search` rows on the in-place `\r` line;
    - at `-v ≥ 3`, each accepted iteration gets its own row, and the gain column shows whether the step helped.
  - The line search has no verbosity setting, and success or failure can already be read from those rows. So the prints are removed instead of being re-routed.

`success`/`failure` lines appear in neither version, because the CLI's affine path never reaches `BacktrackingLineSearch` without crashing (see below). The prints would only show up for direct users of the optimiser. That case is covered by the capsys test.
