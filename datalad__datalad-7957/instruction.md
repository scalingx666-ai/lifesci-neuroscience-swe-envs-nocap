## Overview

Two fixes for saving (and `run`ning) on heavy datasets:

### 1. `save` feeds untracked files to a single `git annex add --batch`

`AnnexRepo._save_add()` gave every file to `git annex add` on its command line, split into chunks. With many files that restarts git-annex for every chunk, and the long command lines were implicated in #7568 (tight ulimits on a many-core node).

Untracked files are now fed via stdin to one `git annex add --batch -z --no-check-gitignore`. Any other path still goes on the command line, as before, because `git annex add --batch` behaves differently from the non-batch mode (checked with git-annex 10.20260901):

| input | non-batch | `--batch` |
|---|---|---|
| file in a nested, unregistered repo | skipped | **added to the superproject** (what made #6977 fail `test_save_typechange`) |
| file within a registered submodule | skipped | **git-annex dies; files it already reported as added are not staged** |
| unmodified/already staged tracked file | skipped | re-added (duplicate `add` result for `.gitmodules` in `test_save_subds_change`; without datalad's gitattributes a git-tracked file moves into the annex) |
| directory | recursed | skipped (empty line) |
| vanished file | `FileNotFound` record | empty line, so we produce the not-found record ourselves |
| filename with a newline | n/a | needs `-z` |

So only files that `status()` reports as **untracked**, that are not directories, and that are not under a directory containing `.git` go through batch mode.

`--no-check-gitignore`: batch mode checks every path with `git check-ignore`, and git scans the whole index for each path, so a plain `--batch` was *slower* than chunked command lines on a big index. `status()` never reports ignored files as untracked, so the check is redundant here.

Timing of `git annex add` alone (5000 new files, 200k files already in the index, macOS-sized 128 KiB chunks):

| | time |
|---|---|
| chunked command lines (`maint`) | 35–40 s |
| `--batch -z` | 47–54 s |
| `--batch -z --no-check-gitignore` | 31 s |

Add stage of `datalad save` in the same setup: 37.8 s → 27.8 s (128 KiB chunks), 37.1 s → 27.7 s (Linux's default limit, where `maint` needs just one chunk). With a small index the two modes take about the same time.

Why not just rebase #6977: besides the semantic differences above, it changed the public `AnnexRepo.add_()` to batch any multi-file call, and its lock-step `BatchedAnnex` bypassed `_call_annex()`, losing fake dates, `annex.alwayscommit=false`, the common git options, error mapping and progress reporting. Here `_call_annex_records(..., stdin=...)` keeps all of these.

### 2. Commit messages are passed to git in a file

A single command line argument is limited to 128 KiB on Linux, whatever ARG_MAX or `ulimit -s` say. A `run` record with many expanded inputs exceeds that, so `git commit -m` failed with "Argument list too long" (#7611; the stack-size hint printed with it is a red herring). `git commit`, the `commit-tree` calls for run merge commits and adjusted-branch amends, and `rerun`'s `git merge` now use `-F <tempfile>`.

Known limitation: on an adjusted branch, git-annex's own `sync` (called via `localsync()`) still passes the message on its command line and fails the same way. That needs fixing in git-annex.

## Not addressed here (possible follow-ups)

- Modified tracked files still go on command lines. Batching them safely needs `status()` to expose whether the worktree differs from the index.
- `AnnexRepo.add()`/`add_()` are unchanged.
- `status()` mis-parses filenames that contain a newline (separate, pre-existing bug).
- git-annex upstream: `add --batch` behaviour for nested repos and submodules, the per-path `check-ignore` cost, and adjusted-branch propagation with long messages.
