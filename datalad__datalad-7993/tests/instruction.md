# Issue

**Title:** BF: keep the Windows drive colon unescaped when rendering URL paths

## Description

On Windows, cloning from a local RIA store fails in `git annex init`:

```
datalad clone ria+file:///D:/path/store#<dsid>
...
git-annex: internal error, "/D:/path/store/6ce/b1dc5-..." is not absolute
```

Seen in datalad-next's `test-win` job, as `test_ria_postclone_noannex` and `test_nested_pushclone_cycle_allplatforms`.

### Cause

- `decode_source_spec()` builds the git URL with `str(URL)`.
- `URL._fields_to_pr()` quoted the whole path with `urllib.parse.quote()`, so the remote URL became `file:///D%3A/path/...`.
- Git decodes that, so the clone itself succeeds.
- git-annex's `parseURIPortable` (since 10.20230329) looks for a drive letter *before* unescaping. It does not see one in `D%3A`, keeps the leading slash, and `/D:/...` is then not an absolute Windows path.

### Fix

- Quote the path with the existing `quote_path()`. On Windows it leaves the colon of a leading `/<letter>:/` unescaped, as `Path.as_uri()` and `get_local_file_url(compatibility='git')` already do. Elsewhere, and for any other path, it is the same `urllib.parse.quote()` call as before.
- On Windows this applies to URLs of any scheme, e.g. `http://host/C:/x` is no longer rendered as `http://host/C%3A/x`. A colon is a valid path character (RFC 3986), and both forms decode to the same path.
- Tests:
  - `test_quote_path` checks that `URL(scheme="file", path="/C:/win:xxx")` renders with only the drive colon unescaped on Windows.
  - In `test_url_samples`, `file:///C:/path/sp1` now has to render back exactly on Windows (no more `exact_str=False`).

### Testing

- `datalad.support.tests.test_network`: 34 passed, 3 skipped (Linux).
- No Windows machine was available. I simulated the Windows branch of `test_url_samples` on Linux, with `on_windows=True` and `_check_ri` as is:
  - with the fix, every string assertion passes;
  - on `maint`, it fails at `str(ri) == str(ri_)`.
  - Only the `localpath` assertion cannot be simulated, because it uses the platform's `url2pathname`; this PR does not change it.
- I checked against git-annex 10.20261026's source that `parseURIPortable` accepts the unescaped form.
- Three independent AI reviewers approved this change, the Windows test edit included.
